## Summary

1. NautilusTrader 2.0rc7 has 39 indicator classes, 1 result type
   (`FuzzyCandle`), and 7 enums in `nautilus_trader.indicators`. 37 of the
   39 accept bars. The exceptions are `BookImbalanceRatio` (order book only)
   and `SpreadAnalyzer` (quotes only). 22 also accept quote ticks and trade
   ticks. All of them have
   `update_raw(...)` for plain floats. **[stub] [run]**
2. One `BacktestEngine` run can hold many instruments. A strategy can
   subscribe to the bars of each one, rank them, and rebalance on a timer.
   I ran 500 instruments × 2,500 daily bars in one run. **[run]**
3. Cash is per account, and an account is per venue. One account can hold
   more than one currency (`base_currency=None`), but the engine does not
   convert cash between currencies for a cash account. A USD-only cash
   account cannot buy an HKD instrument. **[run]**
4. `BacktestNode` accepts only 1 run config in 2.0rc7. It cannot run a
   parameter sweep by itself. A sweep is a loop: one engine with
   `reset()` between parameter values, or one new node for each value, or one
   child process for each value. **[source] [run]**
5. Results come back as `BacktestResult` (statistics dicts and a returns
   series) and through `engine.cache` and `engine.portfolio`. The report
   functions (`generate_*_report`) need pandas. ATrade does not install
   pandas. **[stub] [run]**
6. ATrade can reuse the indicators, the multi-instrument engine, the timers,
   and the reset loop. ATrade must write the indicators that NautilusTrader
   does not have (fundamental data) and the universe data load. ATrade must
   also write the multi-currency capital split, the USD conversion, the sweep
   runner, and the result storage. See "Reuse and gaps".

## 1. Built-in indicators

### 1.1 Common interface

- Import: `from nautilus_trader.indicators import <Name>`. The module
  re-exports `_libnautilus.indicators`. **[stub]**
- Each indicator has `name`, `count`, `has_inputs`, `initialized`,
  `handle_bar(bar)`, `update_raw(...)`, and `reset()`. **[stub]**
- `initialized` is `False` until the indicator has enough inputs. Before
  that, `value` is `0.0` (confirmed for `SimpleMovingAverage`,
  `ExponentialMovingAverage`, `RelativeStrengthIndex` after 5 of 20 or 14
  inputs). `reset()` sets `count` to 0 and `initialized` to `False`. **[run]**
- `price_type` (where it exists) selects the quote price (`BID`, `ASK`,
  `MID`) for `handle_quote_tick`. A bar always gives its close. **[stub]**
- `MovingAverageType` values: `Simple`, `Exponential`, `DoubleExponential`,
  `Wilder`, `Hull`. Parameters named `ma_type` take this enum. **[run]**
- Other enums: `RateOfChangeMode` (`Percentage`, `Fraction`, `Ratio`,
  `RatioPercent`, `Log`), `StochasticsDMethod` (`Ratio`, `MovingAverage`),
  and the candle enums `CandleBodySize`, `CandleDirection`, `CandleSize`,
  `CandleWickSize` (outputs of `FuzzyCandlesticks`). **[run]**

### 1.2 Registration in a strategy and warm-up

- `Strategy.register_indicator_for_bars(bar_type, indicator)` registers an
  indicator. There are also `register_indicator_for_quote_ticks` and
  `register_indicator_for_trade_ticks`. `indicators_initialized()` is `True`
  when all registered indicators are initialized. **[stub]**
- The data actor updates the registered indicators before it calls
  `on_bar`. So `on_bar` sees the indicator value that includes the current
  bar. **[source]** (`data_actor.rs`, `handle_bar`, lines 1062 to 1081)
- A `request_bars` response also updates the registered indicators, before
  `on_historical_bars`. This is how the ATrade template warms up indicators
  (backtest section 10.3.1). **[source]** (`data_actor.rs`,
  `handle_bars_response`, lines 1420 to 1435)
- The registration accepts any Python object. The wrapper calls the Python
  methods `handle_bar`, `handle_quote_tick`, `handle_trade_tick`, and reads
  `initialized`. So a user-written Python indicator class with these methods
  also works. **[source]** (`crates/common/src/python/indicators.rs`)
  I did not run a custom Python indicator.

## 2. Many instruments in one backtest

### 2.1 Data, subscriptions, ranking, and periodic rebalance

Test script: 1 venue `XNAS`, a `CASH` account with 100,000 USD, `NETTING`
positions, a zero `FixedFeeModel`, N USD `Equity` instruments with daily
bars. The strategy registers 1 `RateOfChange(20)` for each instrument,
subscribes to each bar type, and starts a timer
`clock.set_timer("rebalance", timedelta(days=20), callback=...)`. At each
timer event it ranks the initialized indicators, sells the instruments that
are not first, and buys the first instrument with
`portfolio.account(venue).balance_free(USD)`. **[run]**

Results:

- `engine.add_data()` once for each instrument works. The engine merges the
  streams by time. **[run]** The upstream docs say the same. **[source]**
  (`apis-and-runs.md`, "Loading data")
- `on_bar` gets the bars of all subscribed bar types. `bar.bar_type.instrument_id`
  tells which instrument. **[run]**
- The timer fires in simulated time: first event on 2025-01-23, 20 days
  after the start, then each 20 days. **[run]**
- `portfolio.net_position(instrument_id)`, `portfolio.account(venue)`,
  `portfolio.equity(venue)`, and `portfolio.net_exposures(venue)` give the
  cash and the positions across all instruments of the account. **[run]**
- Market orders sent from the timer callback filled on the following bars.
  The test had more fills than orders (29 fills for 23 orders). I did not
  find the cause. A rebalance design must handle partial fills. **[run]**
- The look-back rules of ATrade (section 10.3.1) apply to each bar type. A multi-instrument run needs look-back bars for each
  instrument in the catalog. I did not test this.

### 2.2 Cash and currencies

Cash belongs to an account. The backtest engine makes one account for each
venue. **[run]**

| Setup | Result |
|---|---|
| 2 venues (`XNAS` USD cash, `SEHK` HKD cash) | Both buys filled. 2 separate accounts. USD cash cannot pay for an HKD buy. **[run]** |
| 1 venue, `base_currency=None`, balances 100,000 USD and 500,000 HKD | Both buys filled. One account has 2 cash balances. `portfolio.equity(venue)` returns 1 value per currency. **[run]** |
| 1 venue, `base_currency=USD`, only USD cash, HKD instrument | The HKD buy is denied: `Account currency conversion failed: Quote maps must not be empty`. **[run]** |
| Same, plus USD/HKD quotes on a second venue | Still denied. A `CurrencyPair` cannot be added to a venue with a single-currency `CASH` account (`RuntimeError`). **[run]** |

Consequences:

- ATrade uses the exchange as the venue (`SYMBOL.EXCHANGE`). A US universe
  on `NASDAQ`, `NYSE`, and `ARCA` makes 3 accounts with 3 separate cash
  amounts. To share one cash amount, the backtest must map all instruments
  to one simulated venue. That changes the instrument ID compared with the
  forward test. **[run]** (the 2-venue case)
- A US plus Hong Kong universe needs a multi-currency account or 2 accounts.
  The engine does not move cash between USD and HKD. ATrade must split the
  paper capital per currency at the start, as it does now for one
  instrument (section 10.8). ATrade must also convert the equity curve to
  USD outside the engine. **[run]**
- `Cache.get_xrate()` takes a venue argument. The stubs have no Python
  method to set an exchange rate in the cache. **[stub]**
- Portfolio conversion to a base currency uses `MID` xrates from the cache.
  When no xrate exists, PnL and exposure queries fail closed. **[source]**
  (`docs/concepts/portfolio.md`)
- The upstream docs say that portfolio returns need one common currency.
  For multi-currency portfolio returns, convert the balances to one
  currency first and calculate the percent changes outside NautilusTrader.
  **[source]** (`docs/concepts/portfolio.md`, "Multi-currency accounts")

## 3. Batch backtests and parameter sweeps

### 3.1 BacktestNode

- `BacktestNode(configs)` takes a list, but 2.0rc7 refuses more than 1
  config: `Only one run config per BacktestNode is supported (kernel
  MessageBus is a thread-local singleton)`. **[source]**
  (`node.rs`, `validate_configs`, lines 353 to 360) **[run]**
- The upstream docs say: to run independent configurations, create and
  dispose one node at a time. **[source]** (`apis-and-runs.md`, "Use fresh
  nodes for independent runs")
- A `BacktestRunConfig` has `venues` (`BacktestVenueConfig`), `data`
  (`BacktestDataConfig`), `engine`, `id`, `chunk_size`, `start`, `end`,
  `raise_exception`, `dispose_on_completion`. **[stub]**
- `BacktestDataConfig` reads from a `ParquetDataCatalog` (`catalog_path`).
  It takes `instrument_ids` (a list) and `bar_types`. So one data config
  can load bars of many instruments. **[stub]** The node loads the
  instruments from the catalog and fails when a requested instrument is
  missing. **[source]** (`node.rs`, `build_engine`)
- Each `BacktestVenueConfig` needs an explicit `fee_model`. **[source]**
- Strategies: `node.build()`, then `node.add_strategy(run_config_id,
  strategy)`, then `node.run()`. `run()` returns `list[BacktestResult]`.
  **[stub] [run]**
- `chunk_size` (1 to 1,000,000) streams the catalog data in chunks. `None`
  loads all data at once. **[source]**
- In one process, a second node after `dispose()` of the first one ran
  correctly. A new `BacktestEngine` after that also started. **[run]**

### 3.2 One engine, reset between parameter values

- The upstream docs show this loop: `engine.run()`, `engine.reset()`,
  `engine.clear_strategies()`, `engine.add_strategy(next)`, `engine.run()`.
  `reset()` keeps the loaded data, the instruments, and the venues. It
  clears orders, positions, balances, and counters. **[source]**
  (`apis-and-runs.md`, "Repeated runs")
- I ran 4 `RateOfChange` periods (5, 10, 20, 40) on one engine with this
  loop. Each run took 2 to 4 ms (3 instruments × 250 bars). The result for
  period 10 was the same as the `BacktestNode` run with period 10
  (PnL −36,598.15 USD). So the reset gives a clean state. **[run]**

### 3.3 Parallel runs

- The MessageBus is thread-local, and `BacktestNode` is an `unsendable`
  pyo3 class. **[source]** (`node.rs`) A Python strategy also runs its
  callbacks under the GIL. Threads are not a useful way to run backtests
  in parallel. I did not test threads.
- Separate processes are the way to run in parallel. ATrade already runs
  each backtest in its own child process with the backtest limits
  (concurrency, timeout). A sweep can use the same child process and queue.

### 3.4 Result contents

`BacktestResult` **[stub] [run]**:

- `run_config_id`, `run_id`, `trader_id`, `instance_id`.
- `run_started`, `run_finished` (wall-clock UNIX ns), `backtest_start`,
  `backtest_end` (simulated UNIX ns).
- `elapsed_time_secs`: in the test this was the simulated span
  (21,513,600 s = 249 days), not the wall-clock time. **[run]**
- `iterations`, `total_events`, `total_orders`, `total_positions`.
- `summary`: a `dict[str, str]`, for example
  `account.XNAS.balance.USD.total`, `positions.closed`, `orders.total`.
- `stats_pnls`: per currency, for example `PnL (total)`, `PnL% (total)`,
  `Win Rate`, `Expectancy`, `Avg Winner`, `Max Loser`.
- `stats_returns`: `Sharpe Ratio (252 days)`, `Sortino Ratio (252 days)`,
  `Profit Factor`, `Returns Volatility (252 days)`, `Risk Return Ratio`,
  `Tail Ratio`, skewness, kurtosis, average win and loss.
- `stats_general`: for example `Long Ratio`.
- `returns_series`: `dict[int, float]`, one value per day (249 points for
  250 daily bars).

Other result paths:

- `engine.cache.orders()` and the `OrderFilled` events. ATrade reads trades
  this way now (`read_trades()` in `strategy_engine_run.py`).
- `engine.portfolio` and `node.get_engine_portfolio(run_config_id)`.
- `generate_orders_report`, `generate_fills_report`,
  `generate_positions_report`, `generate_account_report` raise
  `ImportError: pandas is required for report generation`. ATrade does not
  install pandas. **[run]**

## 4. Performance

Test machine: the ATrade development machine. The strategy of section 2.1
(Python callbacks for each bar and each timer). Bars were made as Python
`Bar` objects in the same process, so the memory includes them. **[run]**

| Instruments × daily bars | Bars | `engine.run()` | Script wall time | Peak RSS |
|---|---|---|---|---|
| 5 × 250 | 1,250 | 0.006 s | – | – |
| 50 × 1,000 | 50,000 | 0.10 s | 0.19 s | 300 MB |
| 200 × 2,500 | 500,000 | 0.94 s | 1.5 s | 909 MB |
| 500 × 2,500 | 1,250,000 | 2.45 s | 3.75 s | 2,002 MB |

- The engine speed is not a limit for daily-bar universes of some hundred
  instruments. Memory is the first limit: the `web` container limit is
  `ATRADE_WEB_MEMORY_LIMIT` (default `4g`), and the backtest child runs in
  that container.
- `chunk_size` in `BacktestNode`, or `run(streaming=True)` with
  `clear_data()` on the engine, lowers the memory for large data.
  **[source]** I did not measure it.
- The test did not include the PostgreSQL read and the Arrow conversion of
  ATrade. For 1-minute bars the bar count is about 390 times larger per
  trading day. I did not measure minute bars.

## 5. How ATrade runs a backtest now

From `docs/architecture/backtest.md` and `strategy_engine_run.py`:

- A request has 1 instrument, 1 bar period, 1 strategy version. **[source]**
- The child makes 1 `Equity`, 1 venue (the exchange), 1 `CASH` account in
  the instrument currency, `NETTING`, a zero `FixedFeeModel`, and adds the
  bars of the range with `engine.add_data()`. Look-back bars go to a
  temporary `ParquetDataCatalog` for `request_bars`. **[source]**
- The strategy config gets `instrument_id` and `bar_type`. All other fields
  have defaults. There is no parameter input. **[source]**
- The child calculates the equity curve and the metrics itself
  (`calculate_equity_curve`, `calculate_metrics`). It does not use
  `BacktestResult`. **[source]**

## 6. Reuse and gaps

ATrade can reuse:

- The 39 indicators, `register_indicator_for_bars`, and the `request_bars`
  warm-up path. They work in a backtest and in a forward test.
- `update_raw()` of each indicator outside the engine, for example to
  calculate indicator values for a screen from saved bars. **[run]**
- One `BacktestEngine` with many instruments, `subscribe_bars` for each,
  `clock.set_timer` for a periodic rebalance, and `portfolio` queries.
- The `reset()` loop for parameter values on the same data.
- `BacktestResult.stats_returns` (Sharpe, Sortino, profit factor) as a
  source for more metrics, if ATrade accepts that these are not in USD for
  a multi-currency run.

ATrade must write:

- Fundamental indicators and cross-instrument indicators (ranking scores,
  relative strength, correlation). NautilusTrader has none.
- The strategy config for many instruments: a list of instrument IDs and
  bar types in place of 1 `instrument_id` and 1 `bar_type`. This changes
  the strategy file format (strategy section 9.2).
- The data load for a universe: saved bars, look-back bars, and
  `create_instrument()` for each instrument.
- The venue plan: one simulated venue for all US instruments (shared cash),
  or one account per exchange. This is a design decision.
- The multi-currency plan: the split of paper capital per currency, and the
  USD equity curve from saved exchange rates. The engine does not convert
  cash for a cash account.
- The equity curve for many positions. `calculate_equity_curve` now takes
  1 instrument.
- The sweep runner: the parameter grid, one child process (or one reset
  loop) for each value, the queue, and the backtest limits. `BacktestNode` does not do sweeps in 2.0rc7.
- Result storage in PostgreSQL. `BacktestResult` is in memory only. The
  report functions need pandas.

- Memory with `chunk_size` or streaming, and run time with minute bars.
- Whether `routing=True` on a venue lets one account trade instruments of
  other venues.
